# 云端自主工作：让电脑关机也能继续干活

> **一句话**：GitHub Actions 的 runner 跑在 GitHub 的服务器上，**跟你电脑开不开机完全无关**。
> 本仓库已配置好定时巡检；本文说明机制、现状、以及想升级到「AI 云端干活」时怎么做。

---

## 0. 先搞清楚三种「定时」的区别

很多人以为「WorkBuddy 定时任务 = 电脑关了也能跑」，其实不是。官方文档写得很清楚：

| 定时任务来源 | 电脑关机后能跑吗 | 官方原文依据 |
|---|---|---|
| **本地**（客户端创建） | ❌ **不能** | 「本地定时任务在本机客户端中执行，执行期间请勿关闭电脑或退出客户端」 |
| **项目**（项目中创建） | ❌ 不能 | 同上 |
| **云端** | ✅ **能** | 「云端定时任务在云端沙箱中执行，电脑关机或离线时也能按时运行」 |

**所以想「关机也干活」，有两条路**：
1. **GitHub Actions** —— 本仓库已用，零 token 消耗
2. **WorkBuddy 云端定时任务** —— 能跑，但云端沙箱访问不到本机文件

## 1. 本仓库现状：daily-audit 定时巡检

### 它做什么

```
每天 UTC 03:17（港时 11:17）
    ↓
GitHub 云端 runner 检出仓库
    ↓
从 source 分支取 data/ + scripts/
    ↓
python scripts/audit_questions.py --quiet
    ↓
有问题 → 开 Issue（带「巡检」标签）
无问题 → 什么都不做
```

### 关键特性

| 特性 | 说明 |
|---|---|
| **零 token 消耗** | 纯 Python 标准库脚本，**不调用任何 AI** |
| **只读不改** | 发现问题只开 Issue，**绝不自动改题库**（题库是人工校对过的内容） |
| **幂等** | 同一天重复触发不刷屏（按日期去重） |
| **可手动重跑** | Actions 页面点 "Run workflow"，勾 `force` 忽略去重 |
| **权限最小** | `contents: read` + `issues: write`，仅够开 Issue |

### 与 verify.yml 的分工

| | `verify.yml` | `daily-audit.yml` |
|---|---|---|
| 触发 | 每次 push / PR | 每天定时 |
| 作用 | **守门员**：不通过就不能合并 | **体检**：主动找存量问题 |
| 输出 | 失败则 CI 红灯 | 开 Issue 提醒 |
| 阻断性 | 是 | 否 |

## 2. ⚠️ 一个必须知道的 GitHub 规则

> **`schedule`（定时）事件要求 workflow 文件存在于默认分支，否则 Cron 永远不会触发。**
> 而 `push` 事件读的是**推送 ref** 里的 workflow，不受此限制。

本仓库默认分支是 `main`（部署产物分支），且 `main` 上原本**一个 workflow 都没有**。
只把文件加到 `source` 分支 → 定时任务**永远不会跑**。

### 所以 `daily-audit.yml` 在两个分支各存一份

```
main    （默认分支，schedule 从这里读）
source  （push 事件从这里读）
```

**两份内容必须完全一致**。核对方法（不要靠肉眼看）：

```bash
git rev-parse "source:.github/workflows/daily-audit.yml"
git rev-parse "main:.github/workflows/daily-audit.yml"
# 两个哈希相同 → 内容一致
```

### 为什么 job 里要显式检出源码

`main` 是部署产物分支，**没有 `data/` 目录**，题库体检会因找不到 `_pastpaper.json` 而失败：

```bash
git fetch origin source --depth=1
git checkout FETCH_HEAD -- data scripts
```

## 3. 体检输出为什么用 `--quiet` 而不是 `--json`

`audit_questions.py` 有两种输出模式：

- `--json` —— 全量，含**统计类信息**（题型分布、文件/题量、题图共用统计）
- `--quiet` —— 只输出**真正需要处理**的条目（脚本内置 `QUIET_SKIP` 过滤）

**用 `--json` 会导致每天误报**：那些统计信息不是问题，却会被当成"发现 N 个问题"而开 Issue。

`--quiet` 的口径与 `verify_build.py` 的门禁**完全一致** —— 复用既有标准，不要造第二套。

当前实测输出 0 行 → 题库干净 → 不会误报。

## 4. 想升级成「AI 在云端干活」

上面的巡检是纯脚本。要让 **CodeBuddy CLI**（AI）在 Actions 里改代码，需要三步。

### 4.1 申请 API Key

1. 打开 <https://copilot.tencent.com/profile/> 申请 API Key（中国版）
2. 存进 GitHub 仓库 Secrets：`Settings → Secrets and variables → Actions → New repository secret`
   - 名字：`CODEBUDDY_API_KEY`
3. **不要**把 Key 写进任何文件或提交到仓库

### 4.2 认证方式（实测确认）

CI 里**必须用 API Key**，不能用 `/login` 登录态 —— CI 没有交互式登录环境。

实测无 Key 时直接报错：
```
Error: Authentication required. Please use /login command to sign in to your account
```

环境变量：

| 变量 | 用途 |
|---|---|
| `CODEBUDDY_API_KEY` | 仅调模型接口（**CI 用这个**） |
| `CODEBUDDY_AUTH_TOKEN` | 完整平台功能（Token 刷新、计费查询） |
| `CODEBUDDY_INTERNET_ENVIRONMENT` | 中国版必须设 `internal` |

### 4.3 workflow 骨架

```yaml
- name: Install CodeBuddy CLI
  run: npm install -g @tencent-ai/codebuddy-code

- name: Run agent
  env:
    CODEBUDDY_API_KEY: ${{ secrets.CODEBUDDY_API_KEY }}
    CODEBUDDY_INTERNET_ENVIRONMENT: internal
  run: |
    codebuddy -p "你的任务描述" \
      --output-format json \
      -y \
      --allowedTools "Read,Edit,Bash(python:*)"
```

**`-y` 是 `-p` 非交互模式的必需参数** —— 不加的话文件读写、命令执行全被权限拦住。

### 4.4 ⚠️ 公开仓库的风险

**本仓库是公开的**（GitHub API 返回 `"private": false`）。
公开仓库的 Actions 有额度被薅的风险：任何人都能 fork 后触发你的 workflow，消耗你的积分。

启用前必须做：

1. **限制触发条件** —— 只用 `schedule` + `workflow_dispatch`，**不要**用 `pull_request`
   （否则外部 fork 的 PR 就能触发你的付费 AI）
2. **最小权限** —— `contents: read`，不给 `write`
3. **设定预算上限** —— 积分用完自动停，别开成无限扣费
4. **考虑改私有** —— 如果不打算公开协作，私有仓库能从根本上杜绝被薅

## 5. 三档强度怎么选

| | ① 只巡检 + 开 Issue | ② 巡检 + 自动提 PR | ③ 全自动改主线 |
|---|---|---|---|
| AI 做什么 | 只读、定位 | 改代码 + 提 PR | 改代码 + 直接推 source |
| 人工介入 | 看 Issue 决定 | review PR 后合并 | 无 |
| 最坏情况 | 误报 → 忽略 | AI 改错 → **CI 11 项守门员挡住** | AI 误判 → **直接上线，用户看到错答案** |
| 积分消耗 | 低（现在是 0） | 中 | 中 |
| 建议 | ✅ **当前状态** | ✅ 可选 | ❌ 不建议 |

**第三档明确劝退**：题库是人工校对过的内容，AI 误判一个答案就是学生看到错答案，没有回头闸门。
**第二档之所以可接受**，正是因为 CI 那 11 项检查（题数/答案越界/空选项/串题/缺图）会拦住绝大多数错误。

## 7. 换行符规范（.gitattributes）

仓库已配 `.gitattributes`，统一入库为 LF。**修改它时注意**：

| 写法 | 效果 | 评价 |
|---|---|---|
| `text=auto` | **入库时**统一 LF | ✅ 真正解决伪 diff 的关键 |
| `eol=lf` | **检出时**强制工作区为 LF | ❌ 会与已入库的 CRLF 文件冲突，制造整片伪 diff |
| `eol=crlf` | 检出为 CRLF（仅用于 `.bat/.cmd/.ps1`） | ✅ 例外必需（cmd.exe 不认 LF 批处理） |

**验证规则是否正确**：
```bash
git add --renormalize .
git status          # 既有文件应该零误改；有误改说明规则写错了
```
