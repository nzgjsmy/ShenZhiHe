## 三、三类显示问题（用户手机截图反映）

### ① 表格裸露成 `<table><tr><td>…`

**根因**：VLM 给的是 HTML，`mdLite` 走 `inline() → esc()` 把 `<` 转义了。

**修法**：`mdLite` 拦截 `<table>` 原样输出。

**两个坑**：

- **不能转 markdown 表格** —— 原卷大量 colspan（「植物物種數目」横跨两栏），
  转过去会变成表头 3 栏、数据 4 栏的错位表格（2019 Q7 实测）
- **段落收集的 `while` 条件也要加 `!/^<table/`** —— 否则表格行先被当段落吞掉再被转义。
  第一次只加了分支没改 while，**完全没生效**（表格数还是 0）

### ② 多余的答题横线

原卷答题线被读成 `—`，逐行用 `RULE_LINE` 滤掉。

### ③ 幻觉碎片

`福建一任官堂竹府下的另苑`、`進田內外的笈安，。` —— VLM 把答题格附近的手写痕迹读成句子。

两条规则：**纯汉字无标点 8–24 字**、**短句以逗号句号收尾**。

另外两个：整句重复输出两遍（去重时先剥 `(i) ` 前缀）、
`$ ^{{-1}} $` 双大括号（VLM 多转义一层）。

### ④ 2019 Q1 两栏对照表

VLM 把「欄 I／欄 II」读成线性文字：栏标题黏在 (a) 题干末尾，右栏的 A/B/C/D 混进左栏填空项。

**修法**：在 `lq1_build.py` 加**人工修正层 `FIXES`**（按题目 id 打补丁）。

> ⚠️ **不要直接手改 `_lq_p1.json`** —— 它是从 raw 生成的，下次 parse→build 就被覆盖。
> `FIXES` 在 convert 之后套用，重跑不丢。

## 四、五项 UI 改动

### ① 书签跟随滚动（V0.25.18）

原来是 `position:absolute; top:104px`，页面一滚书签就留在原地看不见。

改 `position:fixed`，`right` 用 calc 补偿「纸张居中」：

```css
right: calc(max(50vw - 590px, 46px) - 27px);
```

- 视口 ≥1272：纸缘距右 = `(100vw - 1180) / 2`
- 视口 <1272：纸张撑满，右缘距右固定 46px（body padding）
- 再减书签宽 27px，让**左缘贴住纸缘**

### ② 修书签悬空（V0.25.19）

上一版算成 `50vw - 663px`，**多减了 body 的 46px padding**，书签整片悬空在纸外。

实测 **1920/1400/1280/1200/1000/900 六种视口，间隙全部 0px**。

### ③ 看知识点按钮 toggle（V0.25.18）

原来只能点浮窗右上角的 `✕`（手机上手不好够）。现在同一颗按钮：

```
初始        📖 看知識點
第 1 次点   浮窗打开，按钮变 ✕ 收起知識點（实心底）
第 2 次点   浮窗关闭
```

**细节**：浮窗内部跨课题跳转走 `openPip(pid, true)`，不受 toggle 影响 ——
否则点进去看另一个知识点会被当成「再点一次」直接关掉。

### ④ MC / LQ 改名（V0.25.20）

```
卷一 · 選擇題  →  卷一 · MC
卷二 · 長題目  →  卷二 · LQ
```

副标题里的 `MC` 同步改成「選擇題」（否则「卷一 · MC」下面又写 MC，重复）。

### ⑤ 「開始」按钮（V0.25.20）

**看着怪的真因**：`.dse-hero .go` 是 `background:none` 的裸文字，
**却继承了 `.go` 的 box-shadow** —— 在浅青、浅黄便利贴上变成一块「浮起来的白影」。

改成实心主色胶囊。改完又发现卷二卡的按钮文字几乎看不清：
`.dse-lq .tx span, .dse-lq .go { color:#7a6240 }` 把按钮也染成暖褐，深绿底上对比极低。
**已把 `.go` 从那条规则（含深色版）移出去**。

## 五、AMD 显卡跑 OCR 实验（方案 B）

用户问「CPU 占用低能不能提上去」，进而试「Ollama + Qwen-VL」。

### 安装踩三个坑

| 尝试 | 结果 |
|---|---|
| `winget install Ollama` | 卡死 7.5 分钟，下载缓存 0 字节 |
| 官方 `OllamaSetup.exe` | Inno Setup 6.7.1，在 `cuda_v12\msvcp140.dll` 报 `MoveFile code 5` 后回滚 |
| `innoextract 1.9` | 只支持到 Inno 6.0.5，解不开 |

**解法**：GitHub release 有 **zip 免安装版**（主包 1.6GB + ROCm 增量 246MB），
解压到 `D:\ollama-app` 直接跑，完全绕过安装程序。

```
D:\ollama-app\      3.1GB   Ollama 0.40.14 + ROCm 7.1
D:\ollama-models\   3.2GB   只留 qwen3-vl:4b
```

### GPU 状态

```
WARN  AMD driver is too old        ← ROCm 路径被驱动卡住
INFO  library=Vulkan  Vulkan0  "AMD Radeon RX 6600 XT"  7.2 GiB
INFO  offloaded 29/29 layers to GPU
INFO  CLIP using Vulkan0 backend   ← 视觉编码器也在 GPU
```

**ROCm 用不了，但 Vulkan 接上了**，显卡确实在工作。

### 四模型实测（2019 p023，911 字 + 2 表格）

| 模型 | 耗时 | 表格 | 分值 | 幻觉 |
|---|---|---|---|---|
| PaddleOCR-VL（CPU 基准） | ~300s | HTML+rowspan | ✓ | 无 |
| qwen3-vl:8b | 329s | 6 行全对 | ✓ | 无 |
| **qwen3-vl:4b** | **139s** | 6 行全对 | ✓ | 无 |
| qwen2.5vl:7b | 127s | 缺 1 行 | ✓ | 轻微 |
| qwen2.5vl:3b | 59s | 行错位 | ✗ | **严重** |

**qwen2.5vl:3b 会编造答案提示** —— 原卷是空白答题格，它写出
「我們使用量子計算模型進行仿真研究」。**比漏字危险得多**，学生会当成题目要求。

### 五个参数坑

1. `repeat_penalty=1.25` 会让模型输出**空白**（表格的 `|` 被惩罚掉）→ 用 **1.05**
2. **Qwen3-VL 的 thinking 关不掉**（`think:false` 无效，响应仍有 944 字 thinking），
   `num_predict` 必须 **8192**
3. **整页 1700×2200 一次送会让 Vulkan 崩溃**（`device lost`，HTTP 500）→ 必须切 3 段
4. 切片 overlap 80px 造成段间重复 → 加 `strip_overlap()`
5. 分辨率不能缩，1400 宽会漏表格行和分值 → 保持原卷 1700

### 结论：这次不换

1. 4B 只比 CPU 版快 1.2–2 倍，不是数量级
2. 8GB 显存卡住模型规模，8B 要部分 CPU offload，速度和 CPU 版一样
3. **输出没有结构信息**（无 block_label、无坐标），现有 `lq1_parse.py` 全靠 block_label
   过滤噪声，换模型等于重写解析层
4. PaddleOCR-VL 已在跑，剩 9 份卷 4 小时完成

**什么时候值得用**：化学、物理卷二（300+ 页）时，可 qwen3-vl:4b 初筛 + PaddleOCR-VL 精修。

### 模型清理（测完之后）

四个模型占 18GB，实测完只留最优的那个：

| 模型 | 大小 | 处置 |
|---|---|---|
| **qwen3-vl:4b** | 3.3 GB | ✅ **保留**（速度与质量的最佳平衡点） |
| qwen3-vl:8b | 6.2 GB | 已 `ollama rm` 删除 |
| qwen2.5vl:7b | 6.0 GB | 已 `ollama rm` 删除 |

**模型目录 18GB → 3.2GB，释放 14.8GB**，同时清掉了三个模型的测试输出文件。

删除后重新验证 `qwen3-vl:4b` 仍可用（跑了一次推理，正常输出 78 字）。

## 六、VLM 并发实测（重要，别再重复试）

用户问「CPU 占用 17.7% 能不能提上去」：

- `PaddleOCRVL()` **没有 cpu_threads 参数**，单页是自回归解码，天然单线程
- worker **3 → 5**，实测每页耗时 **300 秒 → 480 秒**，总吞吐不升反降
- 5 个 worker 内存 18.2GB（每个约 3.6GB），CPU 仍只有 5.8%
- **瓶颈在内存带宽，不在核心数。3 个 worker 是甜点**

另外 **4 个 worker 同时跑 9 份卷会 `BrokenProcessPool` 崩掉**，一页都不完成。

## 九、今天的教训（可复用）

### 解析层

1. **表格不能转 markdown** —— colspan/rowspan 会丢，宁可保留 HTML
2. **改了分支还要改 `while` 条件** —— 否则上一层的循环先把数据吃掉了
3. **题号与小问常印在同一块**（`1. (a) 物理屏障…`），只取 group(2) 会整题少一个小题
4. **大题题号会整块丢失** —— 用「同一大题不会出现两个 (a)」推断
5. **页范围按题号顺序算，不是数组顺序** —— 后补题会追加在数组末尾但 page 很小

### 前端

6. **`backdrop-filter` 会破坏子元素 `position:fixed`** —— 它创建包含块
7. **`absolute` 的包含块是 padding box**，不是 border box
8. **裸文字按钮继承 `box-shadow`** 会变成「浮起的白影」
9. **手写体的 ascent/descent 比常规字体大** —— `line-height:1.3` 撑不住

### 部署

10. **`robocopy /MIR /XD .git` 排不掉 worktree 的 `.git`** —— 那是**文件**不是目录，
    要用 `/XF .git`（否则 worktree 当场失效）

### 工具

11. **winget 装大包会卡死**，直接 curl 更快更可控
12. **Inno Setup 安装失败时，先看 GitHub release 有没有 zip 版**

### 识别层（晚上补的）

13. **模型不输出 EOS 会无限生成** —— CPU 满载但 20–60 分钟不出结果，看着像死锁其实是慢跑。
    `PaddleOCRVL.predict()` 的 `max_new_tokens` 是唯一有效手段；`repetition_penalty`
    **本地模型不支持、会被忽略**（日志里有 warning，但很容易看漏）
14. **`ProcessPoolExecutor` 杀不掉正在跑的任务** —— 要中断只能用
    `multiprocessing.Pool.terminate()`，所以并行脚本得自己写停滞检测
15. **「题号回落」当作甲部/乙部断点，必须加下限** —— 只看 `prev > 1` 会被表格行伪造，
    2021 p19 的表格第一格被读成「1.」，一句话切掉乙部前 7 题。改成 `prev >= 20`
16. **导入成功 ≠ 数据正确** —— 每年跑完都要看一眼大题数：乙部常态 11 道，
    7 道说明被误切、10 道说明漏页

### 三处数据缺陷

### 自己引入的一处误伤

V0.25.22 加的「题号回落 = 甲部结束」判据只写了 `prev > 1`。结果 2021 p19 的表格行被读成
「1.」，形成 q7→q1 的假回落，把乙部前 7 题整段当甲部残留切掉了（2021 只剩 7 道）。
判据收紧成 **`prev >= 20`**（甲部 36 题才会出现大数），2021 恢复 11 道。
