## 一、先纠正一个误判

### 看页图（2019 p001）

大題號**不是**独立的加粗标题块，而是 `1(a)` 这种**紧贴正文的行内前缀**：

```
1(a) 為探究雌激素與促卵泡激素（FSH）之間的相互關係，在一時段內，量度一
```

字号与正文相同、不加粗。所以「检测框漏了加粗标题」这个描述从一开始就不成立。

### 看 OCR 原始输出

| 真值 | PP-OCRv4 输出 |
|---|---|
| 甲部 | 聪由 |
| 人體生理學：調節與控制 | 人體生理 :调節与控制 |
| 圖 1 | 圃1 |
| 月經週期 | 调期 |
| 血漿水平變化 | 血水平燮化 |
| `1(a)` | 整块消失 |

「聪由」对「甲部」——字形毫无关系。这是模型在**简体字库**里硬猜。

**根因：PP-OCRv4 的识别字典以简体为主，繁体覆盖率不足。**
题号只是受害者之一，不是独立问题。

### 排除「分辨率」这条路

```python
p = pymupdf.open('2019/2019 卷二.pdf')[0]
p.get_images()  → (1410, 2048)
```

PDF 内嵌原图只有 **1410×2048**，而页图已是 **1700×2200**（200dpi 渲染）。
**已经超采样，再提 DPI 纯属无效功**，源扫描件本身即上限。

### 排除「检测参数」这条路

怀疑 `limit_side_len: 736` + `limit_type: min` 把 1700px 整页缩到 736px。
用配置文件强制改成 `max/2000` 实测：

| 配置 | 块数 | 文字质量 |
|---|---|---|
| min/736（默认） | 22 | 「聪由」 |
| max/2000 + box_thresh 0.3 | 25 | 「聪由」**照错** |

→ 检测召回有提升，**识别质量毫无改善**。这条路排除。

⚠️ 顺带记一个坑：`RapidOCR(det_limit_side_len=2000)` 这种 kwargs **不生效**
（1.4.4 的参数名不匹配，静默忽略），必须走 `config_path=` 改 yaml 才真生效。
当时 A/B/C 三组输出完全一致才发现。

## 三、全量重跑：结果比预想糟

改完 `lq_build.py`，全量重跑 14 份卷二（140 页，5 分钟）。

### 先踩了自己挖的坑

第一次跑完发现 `ocr.json` 的 `page` 字段全变成**块数**（34, 33, 50…）。

原因：我改写内层循环时用了 `for i, box in enumerate(boxes)`，
**覆盖了外层 `for i, page in enumerate(doc)` 的页码变量 `i`**，
于是 `"page": i + 1` 变成了「块索引 + 1」。

改成 `for k, box` 修复。教训：重构循环体时注意变量名遮蔽，
这种 bug 不会报错，只会静默产出错误数据。

### 真正的坏消息

`lq_parse.py` 跑完，**14 年里 11 年退化**：

| 年份 | 旧（v4）大题/推断 | 新（v6）大题/推断 |
|---|---|---|
| 2012 | 7 / 0 | 7 / 0 ✅ |
| 2013 | 6 / 0 | **14 / 11** ❌ |
| 2014 | 5 / 0 | **4 / 0** ❌ |
| 2015 | 7 / 0 | **12 / 6** ❌ |
| 2016 | 7 / 0 | **8 / 0** ❌ |
| 2017 | 6 / 0 | **10 / 3** ❌ |
| 2018 | 7 / 3 | **6 / 0** ❌ |
| 2019 | 9 / 9 | **6 / 0** ❌ |
| 2020 | 10 / 7 | **12 / 11** ❌ |
| 2021 | 12 / 11 | **4 / 0** ❌ |
| 2022 | 8 / 0 | 8 / 0 ✅ |
| 2023 | 8 / 0 | **10 / 5** ❌ |
| PP | 17 / 9 | **22 / 15** ❌ |
| SP | 8 / 0 | 8 / 0 ✅ |

只有 2012 / 2022 / SP 三年保持一致。

### 两种崩坏方式，同一个根因

- **2013**：只有 3 个真锚点（1(a)、1(b)、2(a)），其余靠 x 坐标切分。
  新 OCR 把长句切得更碎 → 过度切分 → 14 道（真实 6 道）。
- **2021**：有 4 个 `(a)` 锚点，parse 就**只信锚点、完全放弃 x 切分**，
  于是 `(b)` 系列全丢 → 4 道（真实 12 道）。

根因：`lq_parse.py` 的策略是「有 big 锚点就只信锚点，没有才用 x 切分」，
**与旧引擎「锚点全有或全无」的分布强耦合**。
新引擎锚点时有时无，两种路径混杂 → 要么过切、要么漏切。

### 最危险的是 2019

`大題=6 推斷=0` —— 看起来「全部有题号、无需补」，实际真实 9 道、漏了 3 道
（`2(a)`、`4(b)` 被静默吞进相邻大题）。

**「推断=0」比「推断=9」危险得多**，因为它不提示你去核对。

## 五、留给下一轮

要用 PP-OCRv6，必须先重写分组逻辑。手头已备好：
- `scratch/_lq_ocr_v4/` 与 `scratch/_lq_ocr_v6/` 两版同源 OCR，可直接对照
- v6 下已知真实结构（2013=6 道、2021=12 道、2019=9 道）

建议方向：不要再用「锚点 vs x 坐标」的二选一策略，改成
**以 Part 边界 + 小问序列为主骨架，锚点只用来定号**——
锚点缺失只影响编号、不影响切分，这样两种引擎都能跑。

## 六、这次学到的

1. **OCR 换引擎不是孤立的**。文字变准 ≠ 下游变好，结构化解析与上游的
   错误模式是强耦合的（parse 的正则和阈值全是针对 v4 的错法调出来的）。
2. **「推断数下降」可能是假好消息**。要看绝对数量和真实性，
   2019 从「推断 9」变「推断 0」实际是退化。
3. **变量名遮蔽是静默 bug**。`for i` 嵌套覆盖外层 `i`，不报错、只产出错数据。
4. **不可靠的告警比没有告警更糟**，会让人放松核对。

### 顺手装的工具：Playwright Python

起因是我说「没有截图工具」，用户让我挑一个。

先查了环境，发现两个**已内置的 skill**（`agent-browser` 1.3.0、`playwright-cli` 0.1.0），
但都要 npm 全局安装 + 下载 Chromium 约 500MB。

又发现系统已有 Chrome 和 Node 22（`verify_build.py` 说「找不到 node」只是 PATH 问题）。
试了 **Chrome headless 零安装截图**：

```bash
"/c/Program Files/Google/Chrome/Application/chrome.exe" --headless=new \
  --screenshot=out.png --window-size=1500,1000 --virtual-time-budget=6000 file:///...
```

能用，但只能静态截图，验证不了交互。

→ 用户选了 **Playwright Python**：`pip install playwright`（40MB），
`launch(channel="chrome")` **复用系统 Chrome，零浏览器下载**。实测可用。

### 做了什么：`scripts/pastpaper/lq_review.py`

单文件 HTML 核对页（图片 base64 内嵌，双击即开）：

- 左页图叠 OCR 框，右块列表
- 按「题号块」的 x 分层：L0（最左，红）/ L1（黄）/ 其他（透明）
- 点条目 → 图上定位；双击 → 标记
- **「显示所有框」开关** → 图上空白处就是 OCR 漏检区
- **「手动补」开关** → 点图任意位置补一个漏检的题号
- 导出 JSON（page/y/x/文字）

14 个年份全量生成，共 23MB。

### Playwright 抓到的两个真 bug（静态截图发现不了）

**bug 1：`W=0 / H=null` 导致所有框垂直位置全错。**
旧版 `lq_build.py` 产出的 `ocr.json` 里 `W=0`、`H` 字段根本不存在。
我写了 `"H": pg.get("H") or 1` 兜底 → `H=1` → 所有 `y/H` 百分比溢出页面。
**框全部飞到页面外**，但静态截图只看到「框很淡几乎看不见」，完全没意识到是坐标错了。
是 Playwright 点手动补时算出 `y=0` 才暴露。

修法：用页图实际尺寸兜底（`Image.open(png).size`），不再用 1。

**bug 2：`for i` 变量遮蔽。**
（上一轮已修，但同类问题记在这里）内层循环 `for i, box in enumerate(boxes)`
覆盖了外层 `for i, page in enumerate(doc)` 的页码变量，
`"page": i + 1` 静默变成「块数 + 1」。

### 验证

用 Playwright 批量跑 14 个 HTML：页签数、条目数、框数全部正常，
**0 个 pageerror**；手动补坐标实测点击 19%/17% → 存回 19.0%/17.0%，精确。
