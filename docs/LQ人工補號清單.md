## 補號方法

> **2026-10-29 晚更新**：改用 `lq_review.py` 做人工核对（见下）。
> 旧的「直接开页图对着看」方式仍可用，但效率低得多。

```bash
# 1. 產生頁圖 + OCR（已完成，快取在 scratch/_lq_pages/）
python scripts/pastpaper/lq_build.py 2019

# 2. 解析成結構化中間物（⚠️ 分組不可靠，見下方警告）
python scripts/pastpaper/lq_parse.py 2019

# 3. 生成人工核对页（★ 推荐）
python scripts/pastpaper/lq_review.py 2019
#    → scratch/_lq_review/2019.html，双击即可看，无需服务器

# 4. 在核对页里标出真正的大題号 → 「导出 JSON」
#    → 2019-marks.json，含每个大題号的 page / y / x / 文字
```

### 核对页怎么用

左页图、右 OCR 块列表：

| 操作 | 效果 |
|---|---|
| 点右侧条目 | 左侧图上高亮定位 |
| 双击条目 | 标成「大題号」（再双击取消） |
| 「显示所有框」 | 图上空白处即 OCR 没读到的区域 |
| 「手动补」+ 点图 | OCR 漏检时手动补一个题号 |
| 「自动标最左层」 | 把所有 L0 块标上，当起点用 |
| 「导出 JSON」 | 下载 `<年>-marks.json` |

标记存 localStorage，关掉再开不会丢。

### ⚠️ 为什么必须人工核对：两个已证实的坑

**坑 1：`lq_parse.py` 会把小题当大题。**
实测 2019 p4 只有一道大題 `2(a)`（下辖 `(i)(ii)(iii)`，`(ii)` 下还有 `(1)(2)`），
但 parse 切出了 `2(a)`、`2(b)`、`2(c)` 三道——它把 `(i)` 认成大題起点，
再把 `(ii)` 推断成 `2(b)`。

→ 所以「39 道待补号」这个数字，统计的其实是 **39 个错误分组**，
不全是「缺题号」。核对时要以页图为准，不要信 parse 的组数。

**坑 2：OCR 会成片漏检，不是个别字错。**
同一页 `2(a)` 的题干首行（含题号那行，共三行），
**v4 和 v6 两版引擎都没识别出来**，块 y 坐标从 313 直接跳到 517。

→ 这是结构性漏检，换引擎、调参数、提 DPI 都救不回（已逐一实测排除）。
只能靠人工在核对页上补。

## VLM 路线：PaddleOCR-VL（2026-10-29 实测）

### 效果：完胜 PP-OCR

同一页（2019 p4）：

| | PP-OCR v4 | PP-OCR v6 | **PaddleOCR-VL** |
|---|---|---|---|
| `2(a)` 题干三行 | 全漏 | 全漏 | **完整读出** |
| 表格 | 没识别 | 没识别 | **`<table>` HTML，含全部数据** |
| 全页块数 | 44（碎片） | 45（碎片） | **11（完整语义单元）** |
| 题号位置 | 散落 | 散落 | **每块行首** |
| 解析出的题数 | 3 道（**错**） | 3 道（**错**） | **1 道（对）** |

关键差异：**VLM 每块是完整语义单元、题号在行首**，所以
`lq_vl_parse.py` 可以直接用正则分类（`2(a)` / `(i)` / `(1)`），
**完全不需要 x 坐标**——这正是旧版把小题当大题的根源。

### 成本：CPU 上约 4 分钟/页

| 项 | 数值 |
|---|---|
| 模型加载 | 约 78 秒（一次性） |
| 单页推理 | **约 240 秒** |
| 2019 全年 10 页 | ≈ 36 分钟 |
| 全量 140 页 | **≈ 9.3 小时** |

瓶颈是 CPU 上的自回归生成。换更小模型没用（0.9B 已是最小的文档 VLM 之一），
关 layout 也省不了多少（生成才是大头）。

### 工具链

```bash

```

## 為什麼某些年份會缺號

> **2026-10-29 更正**：此前记作「大題題號用加粗字體印，RapidOCR 整個漏讀」，
> 实测后不成立。真实情况见下。

### 真实成因（已用页图核对）

大題題號**不是**独立的加粗标题块，而是 `1(a)` 这种**紧贴正文的行内前缀**，
字号与正文相同、不加粗（见 2019 p1：`1(a)為探究雌激素與促卵泡激素…`）。
所以问题不是「检测框漏了标题」，而是**整行识别质量崩了**：

| 真值 | PP-OCRv4 输出 |
|---|---|
| 甲部 | 聪由 |
| 人體生理學：調節與控制 | 人體生理 :调節与控制 |
| 圖 1 | 圃1 |
| 月經週期 | 调期 |
| 血漿水平變化 | 血水平燮化 |
| `1(a)` | 整块消失 |

「聪由」对「甲部」字形毫无关系 → 是模型在**简体字库**里硬猜。
根因是 **PP-OCRv4 的识别字典以简体为主，繁体覆盖率不足**，题号只是受害者之一。

另：PDF 内嵌原图仅 **1410×2048**，而页图已是 1700×2200，
**再提 DPI 是无效功**，源扫描件本身即上限。

實測識別率（越低越糟）：

| 表現 | 年份 |
|---|---|
| 完全無丟失 | 2022、2023、PP、SP |
| 輕微（1 題內） | 2012、2015、2016 |
| 明顯 | 2013、2017、2014、2018 |
| 嚴重 | 2020、2021 |
| 全丟 | 2019 |

相對地，**小問號與分值識別率很高**（小問 88%、分值幾乎全中），
Part 邊界（甲／乙／丙／丁部）**100% 識別**。
所以結構骨架可靠，缺的只是少數大題的號碼。

### 引擎升级实验：PP-OCRv6 更准，但下游会崩（2026-10-29）

试过 `rapidocr 3.10.0`（PP-OCRv6 small），同一页效果质变：

| | PP-OCRv4（现用） | PP-OCRv6（实验） |
|---|---|---|
| 2019 p1 文本块 | 22 | **34** |
| 大題號 `1(a)` | 整块丢失 | 单独成块，score 1.00 |
| 「人體生理學：調節與控制」 | 错 2 字 | 全对 |
| 2019 全年大題號命中 | **0 / 9** | **4 / 9** |

**但不能直接换**：全量重跑 14 份卷二后，`lq_parse.py` 的分组**11 年退化**——
2013 从 6 道炸成 14 道，2021 从 12 道掉成 4 道。

原因：`lq_parse.py` 的策略是「有 big 锚点就只信锚点、没有才用 x 坐标切分」，
与旧引擎「锚点全有或全无」的分布强耦合。新引擎锚点时有时无，
两种路径混杂 → 要么过切、要么漏切。

**已排除的两条路**（别再试）：
- 调 `Det.limit_side_len` / `box_thresh`：只影响检出块数（22→25），文字质量无改善
- 提 DPI：源图 1410×2048 已是上限

**下一步**：要用 v6，必须先重写 `lq_parse.py` 的分组逻辑。
v6 的 OCR 结果已存在 `scratch/_lq_ocr_v6/`（v4 的在 `scratch/_lq_ocr_v4/`），
可直接拿来对照调试。`lq_build.py` 已加 `LQ_OCR_ENGINE` 开关，默认 `v4`。
